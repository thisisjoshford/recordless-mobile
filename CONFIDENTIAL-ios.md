# Recordless for iPhone

The iOS counterpart of the desktop app's `CONFIDENTIAL.md` design, for anyone who wants confidential
meeting notes without retaining recordings or verbatim transcripts. The
encrypted notes store is called the "vault" in code and this document, and the
"notebook" in the app. This is a phase-0 build; where iOS differs from desktop,
this document says so.

## Protection target

Someone who later gets the app's files should find **no app-created audio or
transcript files**, and saved notes should need this device's Secure Enclave and
its owner (Face ID or passcode) to open. This reduces what can be recovered; it
is **not a forensic-erasure guarantee**. Malware or a compromised OS running
during a meeting or while the notebook is unlocked can still capture content.

As on desktop, **notes are written on the device by default**: a local model
(Qwen 3.5 2B, llama.cpp) runs inside the app and nothing leaves the iPhone.
The private cloud (a NEAR AI model in a verified secure enclave, TEE) is an
option chosen per run on the Notes screen. Speech-to-text always stays on the
device.

## How it works

1. **Unlock.** The notebook (`notebook.vault`, SQLCipher) is keyed with a random
   32-byte raw key generated by the Rust core (`generate_vault_key`), not a
   passphrase, so there is no passphrase to guess offline. The app wraps that key
   with a Secure Enclave P-256 key (ECIES) whose use needs user presence (Face
   ID, or the device passcode as fallback); the wrapped key is kept in the
   keychain as `WhenPasscodeSetThisDeviceOnly`, so it is not backed up and does
   not leave the device. Unlocking decrypts the key inside the Secure Enclave,
   opens the vault, and wipes the Swift copies it holds (see Limits for the
   ones it cannot reach). Removing the device passcode makes
   iOS destroy the wrapping key; the notebook can then not be opened and is set
   aside, never deleted. There is no reset. The vault directory uses
   `NSFileProtectionComplete`. SQLCipher encrypts the database and journal;
   temporary tables stay in memory. The simulator has no Secure Enclave, so the
   notebook is unavailable there. The notebook locks when the app goes to the
   background, unless there is unfinished work (step 7).
2. **Start.** Before capture the core disables core dumps, checks that locked
   (`mlock`) memory is available, and loads the downloaded Whisper model. Any
   failure prevents capture. **There is no sandboxed worker process on iOS**: an
   app cannot spawn helpers, so speech runs on a thread inside the app process,
   which also has network access (for model downloads and the attested notes
   request). Desktop's "the speech worker cannot reach the network" does not
   hold here; the guarantee is only that the core never sends audio or
   transcript text anywhere except inside the attested request in step 5,
   and only when the private cloud was chosen.
3. **Process in memory.** Only the **microphone** is captured (no system or
   other-app audio; iOS does not allow it). Audio is converted to 16 kHz mono
   PCM and voice-activity filtered in memory; no audio files, checkpoints or
   recordings folder are created. Background audio mode keeps capture running
   with the screen locked. Transcript segments are held in page-aligned,
   `mlock`ed memory that is zeroed on release. Swift receives counts, timings
   and one coarse loudness value, never transcript text.
4. **Stop.** Capture stops, queued audio drains, and the Whisper model is
   unloaded before notes can be requested. A locked-memory failure is reported
   from `stop()`; failed inference for part of the audio keeps what succeeded
   and marks the session incomplete. Unprocessed audio is lost on exit or
   crash by design.
5. **Generate notes (on this device by default, or private cloud).** The
   Notes screen chooses where: **On this device** (the default) or **Private
   cloud**. It offers the same scrub categories as desktop, applied identically
   whichever is chosen: names and personal details (enforced by the
   prompt, which tells the model to refer to people by role), email addresses,
   phone numbers, links, and ID/card/account numbers (removed by pattern in
   the Rust core). Every category starts on for each session. Turning one off
   asks for confirmation in a native dialog that names what will no longer be
   scrubbed (and, for the private cloud, that the text goes to the enclave). (Desktop
   raises that dialog from the Rust core because its UI is a webview; on iOS
   the UI is native SwiftUI in the same process, so the dialog is shown by
   Swift and only the flags cross the FFI.) Scrubbing, the privacy rules and
   the prompt are built in Rust; the transcript never crosses the FFI. One notes
   request per session runs at a time.

   **On this device (default).** The downloaded GGUF model (Qwen 3.5 2B Q4_K_M
   on a 6 GB iPhone; the 4B model is offered only with 8 GB or more) is loaded
   by llama.cpp **in the app process**, used and unloaded within the one
   request; the Whisper model is already unloaded by then. It runs on the GPU
   (Metal) by default or on the CPU (a toggle). Nothing is sent anywhere. The
   context is 8k tokens; a long meeting is summarised in parts, combined and
   written up (the same flow as the private cloud and desktop), so it takes
   longer but never needs a larger context. iOS does not let an app use the
   GPU in the background, so the screen is kept on while notes are written; if
   the app is backgrounded anyway the run fails or is cancelled and the
   transcript is kept for retry. Prompts, token lists and output are Rust heap
   (wiped on free); llama.cpp's and ggml's C/C++ heap is wiped as for Whisper
   (Limits). The model weights are read from the file through a read-only
   memory map.

   **Private cloud (optional).**
   **A private cloud model in a verified secure enclave.** For every request
   the core opens one TLS connection to the model's `*.completions.near.ai`
   host (normal WebPKI checks with the built-in webpki root set, via rustls)
   and, before sending any notes text over it, verifies — ported unchanged from
   desktop `summary/nearai/` and tested against the same recorded attestation:
   - the Intel TDX quote against Intel's root of trust, with a non-debug TD and
     a platform status of `UpToDate`, `SWHardeningNeeded` or `OutOfDate`;
   - that the quote binds a fresh random nonce, this connection's TLS public
     key (so TLS ends inside the enclave), and the key that signs responses;
   - that the host says it is serving the requested model;
   - that the measured configuration matches the deployment manifest and the
     replayed boot event log, and that the manifest keeps container logs
     private, takes keys from the attested key service, and pins every image by
     digest;
   - NEAR's deploy-manager log, bound to its own quote from the same enclave
     and produced by a deploy-manager image the measured manifest names (any
     digest the manifest mentions);
   - which image and weights are actually serving the model: the deploy log is
     replayed into the services running now, each compose file is fetched from
     `nearai/cvm-compose-files` at the recorded commit and accepted only at the
     SHA-256 the enclave signed, flags are read as the serving binary reads
     them, and the serving image must be digest-pinned with no variable. Weights
     must name a repository and pass only when pinned to a full commit id;
     otherwise the check is reported **unread**. Every service serving the model
     must agree on weights and revision. A file that fails its hash, or a model
     served from a host-built image, fails the request; a deployment that cannot
     be fetched leaves the check unread;
   - NVIDIA's signed verdict on the GPU evidence for the same nonce.

   Hosts come only from NEAR AI's own TEE host list; there are no custom hosts.
   Any failure stops the request before the prompt is sent. The response must
   then carry a signature from the attested key over the exact request and
   response bytes (and the model id), or it is discarded. Intel's collateral
   service, NVIDIA's attestation service and GitHub receive attestation
   evidence or file requests only. If the host closes the connection while it
   is being verified, a new connection is opened and verified from scratch; the
   prompt only ever travels over a verified connection. A long meeting is split
   into chunks sized from the model's context length, summarised, combined and
   written up; each of those requests is attested separately.

   The app shows a verification summary that expands into every check
   (passed, unread, failed, not run, with what was seen), the Intel platform
   status, the host, the model and elapsed time. A failed verification keeps
   its report, and a failed or cancelled request keeps the transcript for retry.

   Switching apps does not drop the request: it runs inside a UIKit background
   task. If iOS ends the background time first, the app cancels the request
   (the transcript is kept) and says it was interrupted and can be retried.

   **Activation codes and credit.** As on desktop: Recordless provides a NEAR AI
   key from its own workspace, capped by a spend limit, in exchange for an
   **activation code**. The core sends the code to Recordless's credit service
   (`services/trial-keys`, URL compiled in from `RECORDLESS_TRIAL_URL`), which
   returns the key the code unlocks; the key is checked with NEAR AI (an empty
   request that NEAR AI refuses as incomplete only once the key passes, so
   nothing runs and no credit is spent) and only then saved in the vault's
   `private_cloud` table. **The key is never returned to Swift.** When NEAR AI
   turns the key away the core records that the credit ran out; only then does
   the credit status ask the service about the code (sending its account id and
   key, never content), which replies with whether a payment is pending,
   expiry, whether the code was turned off, and an upgrade link. A new code, a
   raised limit, or a later successful run clears the record. Undocumented, a
   NEAR AI key of the user's own (`sk-…`) entered in the code field is checked
   with NEAR AI and saved as is; the credit service never sees it. The credit
   service is not in the notes path and never receives meeting content. The
   key is not secret from a determined user of their own device; the spend
   limit and per-key revocation bound what it can cost. Only the chosen model's
   id is kept in preferences.
6. **Save.** The transcript stays in locked memory after notes are written so
   they can be regenerated (for example with another model). As on desktop, it
   is released and wiped when the notes are saved to the notebook, when the
   session is discarded, when the notebook is locked (only once its notes are
   saved; see step 7), or when the app exits. A failed or cancelled request
   keeps it for retry. The generated notes shown on screen (Swift strings) are
   dropped on lock, but not wiped.
7. **Lock.** The notebook closes when the user locks it and when the app goes
   to the background. As on desktop, locking is **refused** while a meeting is
   recording, notes are being written, or a held transcript has no saved notes
   yet, so going to the background never silently destroys unfinished work:
   the notebook then stays open in the background until that work is finished
   or discarded. While the app stays in the background, the lock is retried
   each time such work ends (a recording stops or is discarded, a notes
   request finishes, fails or is cancelled, or notes are saved), so the
   notebook closes as soon as nothing blocks it (a stopped recording still
   holds an unsaved transcript, which keeps blocking until it is saved or
   discarded). A manual lock explains why it was refused (with a "Discard
   session and lock" option). A transcript kept only for regeneration
   (its notes already saved) does not block lock and is wiped by it. In this
   build saving already releases the transcript, so that case only arises if
   saving is changed to keep it. "Discard session" always works. The decision
   is made in the core (`Session.unfinished_work`, `Session.release_for_lock`),
   atomically with starting a notes request. Unlike desktop, the app does not
   restart on lock. The app-switcher snapshot is covered by a privacy overlay.

The core wipes Rust heap allocations before freeing or reallocating them, and
the C/C++ heap of whisper.cpp and ggml before it is freed (see Limits).
Transcript storage uses `mlock` and is zeroed before release. Core dumps are
disabled before processing. A failed memory lock does not fall back to ordinary
transcript storage.

## What remains on disk

- The encrypted notebook: note titles, timestamps, notes, and the private cloud
  key and credit record.
- The Secure Enclave–wrapped vault key in the keychain (this device only).
- Downloaded Whisper and notes models (excluded from backup) and ordinary
  preferences, including where notes are written, the chosen local and
  private cloud model ids, and the size, modification date and hash of each
  model file already verified.
- Any notes you copy or share outside the app.

## Network

- Model downloads (Hugging Face), started by the user. Whisper URLs are pinned
  to one `ggerganov/whisper.cpp` commit and notes model URLs to one
  `unsloth/Qwen3.5-*-GGUF` commit, and a file is used only if its size
  and SHA-256 match the values compiled into the app (checked before it is
  moved into place, and again for any file on disk not already verified);
  a file that does not match is deleted.
- Private cloud notes, only when chosen: the NEAR AI TEE host for the model (attestation, the
  notes request, its signature), `completions.near.ai` and `cloud-api.near.ai`
  for the host list and model catalogue, Intel PCS, NVIDIA NRAS and
  `raw.githubusercontent.com` for attestation evidence.
- The credit service, only when a code is redeemed or the credit status is
  checked after a run-out.
- There is **no self-updater**: updates come from the App Store or TestFlight.
  There is no telemetry and no feedback form in this build.

## Limits and prerequisites

- With **Private cloud** chosen, notes leave the device (scrubbed as chosen)
  to the attested NEAR AI enclave. For sessions that must not leave the
  device, keep the default, **On this device**.
- On-device notes from a 2B model are less thorough than a large cloud
  model's; review them.
- The TEE checks prove genuine hardware, an encrypted channel into it, and
  which deployment NEAR is running. The platform status is often `OutOfDate`
  (known Intel advisories not yet patched), NEAR shares one TLS key across its
  enclaves, and some checks can be unread; the summary shows which.
- **No worker isolation.** Speech, scrubbing and the attested request all run
  in the app process, which has network access. A memory-safety bug in
  whisper.cpp/ggml, SQLCipher or the TLS/attestation stack is a bug in a
  process that can reach the network. The same holds for llama.cpp, which
  parses the downloaded (hash-pinned) model file in process. Desktop's
  Seatbelt-sandboxed workers have no iOS equivalent; the iOS app sandbox is
  the only boundary.
- Only the explicitly locked transcript buffers are guaranteed by `mlock` not
  to be paged out. iOS may compress or swap app memory. See
  [libsodium's memory-management notes](https://doc.libsodium.org/memory_management).
- **What is wiped before it is freed.** Rust heap (the core's global
  allocator). whisper.cpp, llama.cpp and ggml's C/C++ heap (one ggml, shared by
  speech and notes), two ways (`core/native/`):
  - The core replaces the global C++ `operator new`/`delete` (all 20 sized,
    aligned, array and nothrow forms); `delete` zeroes the whole malloc block
    (`malloc_size`, `memset_s`) before `free`. whisper.cpp's `std::string` /
    `std::vector` / `new` (segment text, token ids, mel spectrogram, model
    loading buffers) bind to it at link time; the build checks that the
    operators are in the archive and the host tests check that string, vector
    and aligned deletes are zeroed. Through dyld's weak-definition coalescing
    the replacement is process-wide, so C++ `delete` in system libraries
    (libc++ itself, as a host test shows) also zeroes; this is harmless but
    costs time on every delete.
  - whisper.cpp, llama.cpp and ggml are compiled with a header that redirects
    their `free`/`realloc` to wiping versions (the build fails if any of their
    objects still calls `free`/`realloc` directly). On iOS ggml allocates its
    CPU buffers (weights, KV cache, compute buffers holding audio features and
    activations) and its Metal shared buffers (the unified-memory host
    allocation the GPU uses) with `posix_memalign` and releases them with
    `free`, so these are zeroed by the CPU when the whisper state is freed (at
    `stop()`/`discard()`) and when the notes model's contexts (KV cache,
    compute buffers) are freed at the end of each on-device run. This is done at the allocator rather than with
    `ggml_backend_buffer_clear`, because whisper.cpp's state is opaque to the
    core and frees its buffers internally.
- **What is not wiped.** Memory freed with plain `free` outside whisper.cpp,
  llama.cpp and ggml (and one llama-cpp-sys-2 helper that frees grammar and
  chat-template strings the core never requests):
  system frameworks (Metal, Accelerate/BLAS scratch, AVFoundation capture
  buffers, Foundation, the Swift runtime), SQLCipher, OpenSSL and ring (they
  wipe their own key material, not every buffer); Metal **private** (GPU-only)
  buffers, used only if the device reports no shared buffers; GPU caches,
  driver and kernel copies, freed pages handed back to the kernel, and thread
  stacks; Swift strings, including the generated notes, the note text read from
  the notebook, and error messages; and anything still allocated when the app
  is killed or crashes. Zeroing on free does not cover live data, copies the
  compiler keeps in registers or on the stack, or memory iOS has already
  compressed or swapped.
- Disabling core dumps does not defeat a jailbroken device, a privileged
  debugger, OS diagnostics, or another participant's recording.
- The vault key exists in app memory while the notebook is open, and the NEAR AI
  key while a request runs.
- **Vault key copies in Swift.** The app keeps the key in one buffer of its own
  that is zeroed (`memset_s`) after each use, and zeroes the buffer it came
  from: the `Data` lifted from `generate_vault_key` (in place; it is the only
  reference) and the CFData returned by Secure Enclave decryption (written
  through its byte pointer). The key is handed to Security and to the core as
  no-copy views of that buffer. Copies it cannot wipe: UniFFI's generated
  lift/lower code reads the key into a temporary Swift `[UInt8]` when it comes
  back from `generate_vault_key` and writes it into another (possibly
  reallocated as it grows) before copying it to a Rust buffer for
  `Vault.create`/`Vault.open`; those Swift arrays are freed without zeroing.
  (The Rust buffers are zeroed by the core's allocator.) Copies made inside
  Security / the Secure Enclave framework are also out of reach.
- Pattern scrubbing cannot reliably remove names or all identifying details.
  Turning scrubbing off sends spoken names, contact details and numbers to the
  enclave and may put them in the notes. Review notes before sharing.
- A request continues in the background only as long as iOS grants background
  time (typically about 30 seconds, not guaranteed); after that it is cancelled
  and the transcript is kept for retry.
- While unfinished work blocks the lock, the notebook (and its key) stays open
  in app memory in the background.
- Microphone only: remote participants are captured only as far as the
  iPhone's microphone hears them.

## Validation and building

```sh
cargo test -p recordless_core          # includes the attestation tests on recorded evidence
./scripts/build-xcframework.sh         # RECORDLESS_TRIAL_URL=https://… to enable activation codes
cd ios && xcodegen generate && xcodebuild -project Recordless.xcodeproj \
  -scheme Recordless -destination 'generic/platform=iOS Simulator' build
```

The vault test writes a canary note and checks the database and WAL for
plaintext and rejects a wrong key. Live NEAR AI checks are opt-in and ignored by
default (`cargo test -p recordless_core nearai_live -- --ignored`). These tests
cover specific behaviours; they do not certify the absence of all forensic
traces.
